**Шифр:** ISHEIKA-NTR-AI · **Редакция:** 1.5.1 (ТЗ-01…ТЗ-06 + ведомость корректирующих изменений v1.1, ИД-01…ИД-23;

ред. 1.5.0 — технический перевод найденной НТ-информации на русский язык (этап 4 «Перевод»,

детали клиентских событий, см. `docs/ACCEPTANCE.md`)
**Назначение:** онлайн-система открытой научно-технической разведки (НТР) с мультиагентным ИИ,
расчётным ядром и доказательной базой.

Реализованы: реестр из **806 источников** и **35 стран**, 24 коннектора (14 подтверждены живыми
запросами), 12-этапный вычислительный процесс, 12 ИИ-агентов A01–A12, расчётное ядро
(релевантность, TRL, реализуемость, барьеры, альтернативы, тренды, прогноз 0–50 лет),

отчёты в **6 форматах**, REST API (**97 маршрутов** + SSE + OpenAPI 3.1),
веб-интерфейс **UI-01…UI-32** с модулями **M01–M33**, сквозная трассировка запросов,
**журнал действий времени работы** (сервер + браузер) с группировкой дефектов и
**диагностикой противоречий** (11 правил, 21 код находок),
SLO доступности с алертами и резервное копирование с проверкой восстановления.

## 1. Быстрый старт

### Windows: единый файл запуска

`release/ISHEIKA-NTR-AI.exe` — один файл, ничего устанавливать не нужно: внутри
встроенный CPython 3.11 (x64) и приложение. Двойной щелчок → «Да» → откроется окно
сервера и браузер на `http://127.0.0.1:8000/` (если порт занят — следующий свободный).
Данные сохраняются в `%LOCALAPPDATA%\IsheikaNTR-AI`, временный каталог распаковки
удаляется при выходе.

Запуск после распаковки выполняется через `ExecuteFile="cmd.exe"` +
`ExecuteParameters="/c isheika.cmd"` (ShellExecuteEx). **Не** через `RunProgram`:
модуль 7zSD.sfx выполняет его как `CreateProcess(NULL, ".\" + RunProgram)`,
поэтому команда с аргументами превращается в путь `.\cmd` и даёт ошибку
«Не удается найти указанный файл» (регрессионный тест `PKG-01`).
Имя сценария — `isheika.cmd`, а не `start.cmd`: имя `start.cmd` парсер cmd
принимает за внутреннюю команду `START` (проверено исполнением, тест `PKG-02`).

Если политика безопасности запрещает запуск SFX-файла, используйте
`release/ISHEIKA-NTR-AI-portable.zip`: распаковать в любой каталог и запустить
`isheika.cmd` — содержимое то же самое.

Пересборка и проверки: `python3 tools/build_exe.py --verify-launch --verify-wine --verify-tests`
(нужен 7-Zip; результаты — в `release/BUILD-INFO.json`).

Требуется только **Python 3.11+** — внешних зависимостей нет.

```bash

python3 run.py                      # профиль DEV, http://0.0.0.0:8000
python3 run.py --port 8080
python3 run.py --no-network         # полностью офлайн (имитационный коннектор)
python3 run.py --email you@org.ru   # polite pool Crossref / Unpaywall
```

Откройте `http://localhost:8000`. Демо-учётные записи профиля DEV (пароль `dev:<логин>`):

| Логин | Роль | Права |
|---|---|---|
| `admin` | администратор | всё, включая ключи и настройки |
| `lead` | руководитель исследования | исследования, реестры, ключи, отчёты |
| `analyst` | аналитик НТР | исследования, аналитика, доказательства, отчёты |

В профилях PILOT/PROD демо-вход заменяется корпоративной аутентификацией (см. `ROADMAP.md`).

### Журнал действий и поиск противоречий (ред. 1.4.0)

Во время работы система ведёт **сквозной журнал** в таблице `ops_journal`: что было
сделано, кем, сколько длилось, чем закончилось и где сломалось. Журнал не подменяет
аудит: аудит отвечает «кто изменил данные», журнал — «что делала система и почему отказала».
Записи связаны с трассировкой (`request_id`, `correlation_id`) и загрузкой (`boot_id`),
поэтому от ошибки в браузере можно дойти до конкретного этапа и SQL-контекста.

Пишется автоматически:

* **обращения к API** — метод, шаблон пути (`POST /api/v1/researches/{id}/start`), HTTP-статус,
  код ошибки, длительность, пользователь и роль (успешные `GET` — уровень `debug`, по умолчанию не пишутся);
* **доменные действия** — создание/запуск/отмена, отчёты, ключи, настройки, входы и отказы доступа;
* **этапы исследования** — старт, finish, отказ этапа с traceback;
* **внешние вызовы** — коннекторы и провайдеры ИИ: адрес, статус, длительность, код ошибки;
* **необработанные исключения сервера** — тип, сообщение, полный traceback, подпись дефекта;
* **ошибки браузера** — `error`, `unhandledrejection`, отказы отрисовки экранов, ответы API
  с `5xx`/`E_INTERNAL`/`E_SCHEMA`/`E_PROVIDER`, сетевые отказы и таймауты, а также шаги
  загрузки с FAIL (`POST /api/v1/journal/client`, доступен без входа, ≤ 60 событий/мин с адреса).

Каждая запись несёт уровень (`debug`/`info`/`warn`/`error`/`critical`), вид
(`action`/`api`/`workflow`/`connector`/`ai`/`analytics`/`storage`/`security`/`ui`/`system`),
исход (`ok`/`fail`/`contradiction`), объект и исследование. Секреты (`password`, `token`,
`api_key`, `authorization`, `cookie`, `Bearer …`, `?key=…`) **маскируются до записи**.
Повторяющиеся падения получают **подпись дефекта** (`fingerprint` — хеш от вида, действия,
типа исключения, кода и нормализованного сообщения с последним кадром стека), поэтому
«одна и та же ошибка 40 раз» видна одной строкой, а не сорока.

Журнал не может уронить работу: запись никогда не бросает исключение, при отказе БД
строка уходит в `var/journal-fallback.log`, а счётчик сбоев показывается на экране.
Хранение — `journal_retention_days` (30 сут.) и `journal_max_rows` (200 000), ротация
выполняется планировщиком раз в час и вручную `POST /api/v1/journal/prune`.

**Диагностика противоречий** (`isheika/diagnostics.py`, 11 правил) ищет не отказы, а
несогласованность данных и нарушение правил ТЗ:

| Код | Что ищет |
|---|---|
| DIA-01a/b/c | «completed» с проваленными этапами; «running» без активных заданий; задание висит > 30 мин |
| DIA-02 | переход состояния, запрещённый конечным автоматом |
| DIA-03 | отчёт в статусе «готов», но файлов на диске нет |
| DIA-04 / DIA-05 | утверждение SUPPORTED/PARTIAL без доказательств; доказательство из чужого исследования |
| DIA-06 / DIA-07 | класс релевантности не соответствует порогу; нет всех шести компонент |
| DIA-08 | TRL выше уровня с выполненными обязательными критериями (усреднение запрещено) |
| DIA-09 / DIA-10 | неизвестный фактор учтён как число; интерпретация при недостаточном покрытии |
| DIA-11 / DIA-12 | немонотонная `P(T ≤ t)`; количественный прогноз на 20–50 лет |
| DIA-13 / DIA-14 | платный провайдер при запрете платного ИИ; квота сверх лимита |
| DIA-15…18 | повторяющийся дефект (одна подпись ≥ 3 раз); повторяющиеся ошибки интерфейса; похожее на секрет в журнале; сбои записи журнала |
| DIA-19 | расчёт ссылается на неизвестную версию методики |

Каждая находка содержит severity, число случаев, **до 10 конкретных свидетельств** (идентификаторы
записей) и рекомендацию; отказ одного правила не отменяет остальные — он попадает
в `broken_rules` и в журнал. Правила проверяются не только внесением противоречия, но и
отсутствием находок на штатном состоянии: прогон на реальном исследовании выявил и устранил
две ложные находки самого анализатора (формат версии методики «CODE version» и штатное
ограничение интерпретации при низком покрытии) — см. `docs/ACCEPTANCE.md`. Проверка запускается кнопкой на экране или
`POST /api/v1/diagnostics/run` (можно записать находки в журнал как `outcome=contradiction`).

Экран **UI-32 «Журнал действий и диагностика»** (M33, право `logs.read`): лента с фильтрами
(уровень, вид, источник, исход, исследование, поиск), KPI за 24 ч, самые медленные действия,
карточка записи с traceback и всей трассировкой, вкладки «Ошибки и дефекты» (группировка
по подписи), «Противоречия», «Ошибки браузера», выгрузка **TXT / JSON / CSV**.

```bash
# то же самое из командной строки
GET  /api/v1/journal?level=error&kind=api&limit=100     # лента с фильтрами
GET  /api/v1/journal/<id>                               # запись + контекст трассировки
GET  /api/v1/journal/errors                             # группы дефектов по подписи
GET  /api/v1/journal/stats                              # счётчики, медленные действия, сбои записи
GET  /api/v1/journal/export?fmt=csv                     # выгрузка (txt|json|csv)
GET  /api/v1/diagnostics?research_id=<id>               # проверка противоречий
POST /api/v1/diagnostics/run                            # проверка + запись находок в журнал
POST /api/v1/journal/prune                              # ротация по политике хранения
```

Настройки (`isheika/config.py`): `journal_enabled`, `journal_level`, `journal_retention_days`,
`journal_max_rows`, `journal_client_rate`, `journal_stack_in_response` (traceback в ответе API —
по умолчанию выключен, чтобы не раскрывать внутренности). Регрессионные испытания:
`JRN-01`…`JRN-16` и `DIA-01`…`DIA-19` (`tests/test_journal.py`, 35 тестов), проверки журнала в
`tools/api_check.py` и 9 проверок экрана в `tools/ui_check.mjs`.

### Если сервер стал недоступен (ред. 1.4.1, ИД-14)

Раньше один отказ сети оставлял экран с ошибкой `E_NETWORK` до перезагрузки
страницы, а ошибки интерфейса после первого же отказа переставали отправляться
насовсем. Теперь:

* **безопасные запросы повторяются сами** — до 3 попыток с растущей паузой
  (изменяющие запросы не повторяются, чтобы не задвоить действие; повтор допустим
  только с `Idempotency-Key`);
* **ответ шлюза 502/503/504 без тела API** считается недоступностью сервера, а не
  ошибкой данных — именно так выглядит остановленный или перезапускающийся сервер
  за прокси;
* **автопереподключение**: при отказе включается проба `GET /api/v1/system`
  (4 с → до 15 с), и когда сервер отвечает, экран **перерисовывается сам**,
  в строке состояния видно «недоступно — переподключение, попытка N»;
* **очередь событий журнала**: недоставленные ошибки браузера хранятся в
  `localStorage` (не более 50) и досылаются после восстановления с отметкой
  `queued_at` — видно, что отказ случился раньше, чем запись попала в журнал;
  размер очереди показан в строке состояния и на вкладке «Ошибки браузера»
  с кнопкой «Отправить очередь»;
* **частичная доступность экрана**: если сводка журнала не получена, лента всё
  равно показывается с предупреждением, а не сменяется экраном ошибки;
* в блоке ошибки есть кнопки **«Повторить»** и **«Переподключиться»**.

Регрессионные испытания: `NET-01`…`NET-08` и `JRN-17` (`tests/test_offline_ui.py`),
а также 9 поведенческих проверок в `tools/ui_check.mjs` — отказ сети, ответ шлюза,
очередь, автоматическое восстановление по таймеру и досылка очереди на сервер.

### Исправления по журналу пользователя (ред. 1.4.2, ИД-15)

Присланный журнал действий и лог событий с рабочей машины позволили найти и закрыть
три дефекта, которые не воспроизводились в автотестах:

1. **Повторный запуск исследования падал на этапе 3.** `KeyError: 'parsed_query'`:
   завершённые этапы при продолжении пропускаются, живых объектов в контексте нет.
   Теперь разобранный запрос, расширение и идентификатор запуска восстанавливаются
   из сохранённого состояния (`RES-01`…`RES-05`).
2. **«Cannot set properties of null (setting 'innerHTML')» на UI-01 и UI-23.**
   Вход в систему запускал две параллельные отрисовки (смена `location.hash` +
   явный вызов), вторая подменяла разметку. Отрисовки идут строго по очереди,
   запись в узлы — через `App.setHTML`, устаревшая отрисовка не трогает DOM,
   слушатели событий экрана снимаются при любой перерисовке (`RND-01`…`RND-05`).
3. **Ложный алерт `COMPONENT_DOWN` по хранилищу.** Параллельные пробы удаляли общий
   файл `.slo-probe` друг у друга (`FileNotFoundError` на Windows). Имя пробы
   уникально, удаление терпимо к отсутствию файла, запись проверяется чтением
   (`SLO-09`).

Дополнительно сводка этапа 4 больше не выглядит противоречием: «дубль» в общем
корпусе означает «документ уже был известен, в том числе из другого исследования»,
поэтому рядом с `unique`/`duplicates` показываются `new_in_corpus` и `known_before`
(`RES-06`).

### Доверие сертификатам источников (ред. 1.4.3, ИД-16)

По журналу с рабочей машины: исследование дошло до конца (106 документов), но
источник **arXiv** отказал с `SSL: CERTIFICATE_VERIFY_FAILED … unable to get local
issuer certificate`. Причина не в сети: сертификат `export.arxiv.org` подписан
удостоверяющим центром «Certainly Root R1/E1», корня которого не было в хранилище
сертификатов Windows. Встраиваемый CPython доверял только хранилищу ОС, поэтому
часть источников была недоступна, хотя в браузере те же адреса открывались.

Что сделано:

* приложение возит **собственный набор корней** `isheika/data/cacert.pem`
  (корни Mozilla NSS, 150 сертификатов, MPL-2.0) и добавляет его к системному
  доверию — доверие больше не зависит от обновлений корней на машине;
* свой набор (корпоративный прокси, свой УЦ) подключается переменной окружения
  **`ISHEIKA_CA_BUNDLE=<путь к .pem>`**; проверка сертификатов **не отключается**
  ни при каких настройках — небезопасного режима в приложении нет;
* отказ проверки сертификата помечается неповторимым (повтор его не лечит) и
  несёт пояснение оператору; в журнале вместо трёх одинаковых записей — одна;
* состояние доверия видно в журнале загрузки (`✓ Доверенные сертификаты на месте`,
  строка «Доверие сертификатам» в окне самопроверки) и в диагностике:
  **DIA-20** «Источник не прошёл проверку сертификата», **DIA-21** «Набор корневых
  сертификатов не найден».

Регрессионные испытания `TLS-01`…`TLS-05` (`tests/test_tls.py`) поднимают локальный
HTTPS-сервер с сертификатом от заведомо неизвестного центра: без дополнительного
набора запрос падает так же, как у пользователя, с набором — проходит, проверка
остаётся включённой.

### Эксплуатация: доступность и резервные копии (P6)

```bash
python3 run.py --backup                       # копия состояния + проверка целостности
python3 run.py --list-backups                 # реестр копий
python3 run.py --verify-backup <ID|путь>      # проверка без восстановления
python3 run.py --restore <ID|путь> --yes      # восстановление (сервер остановлен)
```

Доступность измеряется самопроверками подсистем `api`/`database`/`storage`
(шаг 60 с), цель — **98 % за месяц** (ТЗ-01). Экран **UI-31 «Эксплуатация»**
показывает окна 24 ч / 7 сут / 30 сут, бюджет ошибок и скорость его расхода,
алерты с числовыми основаниями и реестр копий. Регламент — `docs/RECOVERY.md`.

## 4. Что реализовано по ТЗ

**ТЗ-01 (функциональная модель).** Модули M01–M33 доступны из левого меню; 6 ролей RBAC;
настраиваемый реестр (добавление источника не требует изменения ядра); статусы заданий
`queued/running/partial/completed/failed/cancelled`; идемпотентные ключи этапов и продолжение
прерванного исследования; экспорт HTML/PDF/DOCX/XLSX/JSON/CSV; ключи только на сервере
в зашифрованном виде; защита от XSS (экранирование), SSRF (запрет приватных адресов),
инъекций в промпты, обхода paywall/CAPTCHA/авторизации (стоп-лист STOP-01…06), соблюдение
robots.txt и лицензий.

**ТЗ-02 (мульти-ИИ).** Free-first маршрутизация `Q(m,t) = argmax`: бесплатная подтверждённая →
бесплатная альтернативная → локальная → платная **только при явном разрешении**; 18 провайдеров,
11 моделей, адаптер на провайдера; полный контракт запроса/ответа (`request_id`, `task_id`,
`agent_id`, `provider_id`, `model_id`, `prompt_version`, `prompt_hash`, `privacy_class`,
`usage`, `latency_ms`, `estimated_cost`, `finish_reason`, `error_code`); валидация JSON Schema
с ограниченной попыткой исправления и статусом `schema_error`; Retry-After + backoff;
9 статусов провайдера; 4 режима коллективного анализа; **голосование моделей не является
доказательством**; квоты берутся из реестра и фактических ответов API, а не зашиваются в код.

**ТЗ-03 (математика).** Расчётное ядро не зависит от ИИ и версионируется (`M-1.0.0` + хеш входов).
`R = 0,30S + 0,25T + 0,15C + 0,15E + 0,10K + 0,05F`, пороги 0,80 / 0,60;
`claim_id` + Evidence, типы FACT/ANALYSIS/HYPOTHESIS/FORECAST и статусы
SUPPORTED/PARTIAL/CONTRADICTED/UNVERIFIED/SUPERSEDED; **TRL = максимальный уровень с выполненными
обязательными критериями, усреднение запрещено**; `F = 100·Σ(wᵢxᵢ)/Σ(wᵢaᵢ)`, покрытие `C`,
неизвестный фактор ≠ 0; 11 классов барьеров; альтернативы по единым критериям; прогноз
6 горизонтов (0–2…35–50), 3 сценария, монотонная `P(T≤t)`, на 20–50 годах только качественные
сценарии; метрики Precision@10, nDCG@10, TRL MAE, Brier, покрытие интервалов со статусом
**«калибровка не завершена»**.

**ТЗ-04 (интерфейс).** Экраны UI-01…UI-32; верхняя панель, сворачиваемое меню M01–M33 с
индикатором заданий, рабочая область, контекстная панель, статусная строка; светлая/тёмная темы;
адаптив 1920/1440/1366/планшеты; состояния initial/loading/partial/success/empty/warning/error/
offline/permission_denied; кнопка **«Выбрать все страны»** (повторное нажатие снимает выбор);
инфографика SVG без внешних библиотек (TRL ladder, radar, fan chart, матрица рисков, heatmap,
граф связей) с легендами, единицами, tooltip, текстовой альтернативой и экспортом;
таблицы с сортировкой, фильтром, пагинацией, выбором колонок и выгрузкой CSV.
**UI не пересчитывает научные показатели** — только отображает серверные значения с версией методики.

## 5. Отклонения от рекомендованного стека (зафиксированы честно)

Среда сборки не имеет пакетного менеджера, поэтому ядро реализовано **на стандартной библиотеке**.
Предметная логика отделена от транспорта и хранилища, поэтому переход на промышленный стек
не требует переписывания домена.

| ТЗ рекомендует | Реализовано сейчас | Путь миграции |
|---|---|---|
| FastAPI + uvicorn | `api/server.py` (stdlib `ThreadingHTTPServer`), те же маршруты | `uvicorn isheika.api.adapters_fastapi:app` — готовый адаптер поверх `ROUTES` |
| PostgreSQL | SQLite (`var/isheika.db`), схема по ТЗ-06 | `storage/db.py` — единая точка доступа; DDL совместим по составу полей |
| OpenSearch / PG FTS | собственный лексический поиск + релевантность | заменить `search/manager.py` на поисковый бэкенд, контракты сохранить |
| pgvector + эмбеддинги | лексико-семантическая аппроксимация, в каждом расчёте поле `S_method` | подключить эмбеддинги и переключить `S`, версия методики повышается |
| Redis + Celery | потоковый `workflow/engine.py` с идемпотентностью и resume | очередь заданий выносится за тем же интерфейсом `start/status/cancel` |
| WeasyPrint / python-docx / openpyxl | собственные писатели PDF (встроенный шрифт DejaVu) и OOXML | при наличии WeasyPrint PDF делается из HTML автоматически |
| SSO/OIDC, TLS | токены Bearer + RBAC, HTTP в DEV | TLS и OIDC — на границе (reverse proxy), см. `ROADMAP.md` |

Прочие осознанные ограничения:

* **Живых ключей ИИ нет** → ответы формирует детерминированный экстрактор; каждый такой ответ
  помечен `simulated=1`, в UI показан как «детерминированный экстрактор», в отчёт попадает предупреждение.
* **Калибровка методик не завершена** — веса и пороги стартовые, статус выводится во всех экранах.
* Часть источников требует бесплатного ключа (CORE, Unpaywall, EPO OPS, USPTO ODP) — статус
  `RESTRICTED` до внесения ключа в UI-25; NASA NTRS отвечает 403 без ключа, Semantic Scholar — 429
  без ключа (зафиксировано в `docs/REGISTRY_NOTES.md`).
* Доступность ≥ 98 %/мес — эксплуатационная метрика, в DEV не измеряется; точки мониторинга есть.

## 6. Безопасность

* Ключи — в `var/secrets.enc` (шифрование + HMAC-целостность), в API/UI только факт наличия и маска.
* SSRF: запрет приватных/loopback/link-local адресов и не-HTTP схем.
* Стоп-лист: Sci-Hub/Libgen, автосбор Scholar/ResearchGate/LinkedIn/X, GUI Espacenet,
  PDF CORE в обход API, материалы ДСП/ГОСТ РВ.
* robots.txt соблюдается; исключение `api_terms` — только для документированных официальных API
  (обоснование и журнал — в `docs/REGISTRY_NOTES.md`).
* Prompt injection: контент источников передаётся как данные, инструкции из документов не исполняются.
* Токен передаётся в заголовке `Authorization` (не в cookie) → CSRF-вектор отсутствует;
  для продакшена TLS terminates на границе.
* Аудит: каждое изменение пишет `audit_log`, переходы состояний — `core_state_history`,
  обращения к API — `audit_api_calls`, квоты — `audit_quota_usage`. Журнал выгружается TXT/JSON/CSV.

## 8. Технический перевод НТ-информации (ред. 1.5.0)

Найденные материалы переводятся на русский язык **отдельным этапом 4** вычислительного
процесса (`translation`, между обработкой документов и фильтром релевантности).
Модуль `isheika/translation.py`, таблица `document_translations` (миграция `0007_translation`).

* Язык определяется **по каждому полю** (заголовок, реферат, текст) — русские поля не переводятся.
* Три честных режима: `original` (текст уже на русском), `terminology` (детерминированный
  терминологический черновик по глоссарию **G-1.7.0**, 1366 слов), `ai_technical` (машинный
  перевод подключённым провайдером). Имитационный провайдер для перевода **запрещён**.
* Для каждого перевода сохраняются `coverage` (доля переведённых слов), список
  непереведённых слов, версия глоссария и `source_hash` (кэш — повторный перевод не выполняется).
* Падежное управление и перестановка именных цепочек в детерминированном контуре не
  реализованы, поэтому **все машинные и терминологические переводы помечаются
  `review_required=1`** и в отчёте идут как черновик, требующий редакторской вычитки.
* API: `GET /api/v1/documents/{id}/translation`, `POST /api/v1/researches/{id}/translate`,
  `GET /api/v1/researches/{id}/translation` (сводка по режимам и покрытию).
* Отчёты (HTML/PDF/DOCX/XLSX) содержат русский перевод рядом с оригиналом и полосу покрытия;
  интерфейс — блок перевода в карточке документа (UI-04).

Испытания: `tests/test_translation.py` (TRN-01…TRN-10).
