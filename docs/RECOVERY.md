# Регламент эксплуатации и восстановления (ROADMAP P6, ред. 1.3.0)

Документ описывает штатные действия оператора: измерение доступности, реакцию
на алерты, резервное копирование и восстановление. Все показатели считает
сервер; интерфейс и отчёты их только отображают.

## 1. Цель по доступности и как она измеряется

| Параметр | Значение | Источник |
|---|---|---|
| Цель доступности | **98 % за 30 суток** (ТЗ-01) | `slo.TARGET_AVAILABILITY` |
| Бюджет ошибок | 2 % отказов | `slo.ERROR_BUDGET` |
| Период самопроверки | 60 с | `slo.PROBE_INTERVAL_SEC` |
| Подсистемы | `api`, `database`, `storage` | `slo.COMPONENTS` |
| Окна наблюдения | 24 ч, 7 сут, 30 сут | `slo.WINDOWS` |

Самопроверка — короткая реальная операция: запрос к БД и `PRAGMA quick_check`,
запись/удаление файла в каталоге данных, проверка зарегистрированных маршрутов.
Результат, длительность и причина отказа сохраняются в `service_probes`.

**Доступность = доля успешных самопроверок в окне.** Это оценка по выборке
измерений, а не непрерывный учёт времени: при шаге 60 с погрешность одного отказа —
одна минута на компонент. Оценка простоя в отчёте помечена как расчётная
(`estimated_downtime_minutes`). Если измерений в окне нет, возвращается
`NO_DATA` и `null` — подставлять «100 %» запрещено (тот же принцип, что и для
F/уверенности, ИД-10).

Скорость расхода бюджета (burn rate) = доля отказов / 0,02. Значение 1×
означает расход бюджета ровно за месяц; порог тревоги — 14,4× при не менее
чем 10 измерениях за час.

## 2. Алерты: правила и реакция оператора

| Код | Важность | Условие | Действие оператора |
|---|---|---|---|
| `SLO_AVAILABILITY_30D` | critical | доступность за 30 сут < 98 % | разобрать отказы по компонентам, устранить причину, зафиксировать инцидент |
| `SLO_BURN_RATE_1H` | critical | burn rate ≥ 14,4× (≥ 10 измерений) | немедленная реакция: бюджет будет исчерпан за часы |
| `COMPONENT_DOWN` | critical | последняя самопроверка подсистемы неуспешна | БД — проверить диск и `integrity_check`; хранилище — права и свободное место; транспорт — журнал сервера |
| `CONNECTORS_DEGRADED` | warning | > 30 % проверенных коннекторов недоступны | проверить квоты/ключи, при необходимости отключить источник в реестре |
| `PROVIDERS_UNAVAILABLE` | warning | > 50 % провайдеров ИИ недоступны | проверить ключи и лимиты; работать на бесплатных маршрутах |
| `BACKUP_OVERDUE` | warning | последняя копия старше 168 ч либо копий нет | выполнить `run.py --backup` |

Правила детерминированы и прикладывают **основание** — числа, по которым
принято решение (поле `context`). Алерт закрывается автоматически только при
устранении причины. Подтверждение (`acknowledge`) фиксирует оператора и время,
но **не закрывает** алерт и не создаёт дубликат при следующем пересчёте.

Действия: экран **UI-31 «Эксплуатация»**, вкладки «Алерты» → «Подтвердить»,
«Пересчитать правила»; API `GET /api/v1/alerts`, `POST /api/v1/alerts/evaluate`,
`POST /api/v1/alerts/{id}/acknowledge`.

## 3. Резервное копирование

Состав копии (ZIP, формат `isheika-backup-1`):

* `isheika.db` — согласованный снимок БД через sqlite backup API (корректно при WAL);
* `secrets.enc` — хранилище ключей **в зашифрованном виде**;
* `config.json` — конфигурация профиля;
* `manifest.json` — версия приложения, перечень миграций, счётчики таблиц,
  размер и SHA-256 каждого файла.

Мастер-ключ шифрования в копию **не включается**: храните его отдельно, иначе
ключи из копии восстановить невозможно.

Штатное расписание (DEV/PILOT): копия не реже одного раза в сутки, хранение —
не менее 7 суток; правило `BACKUP_OVERDUE` контролирует давность 168 ч.

```bash
python3 run.py --backup                     # создать и сразу проверить
python3 run.py --backup --backup-dir D:\backups
python3 run.py --list-backups
python3 run.py --verify-backup <ID|путь>
```

Копия считается пригодной, только если пройдены все проверки: CRC записей
архива, наличие манифеста и БД, совпадение SHA-256 каждого файла,
`PRAGMA integrity_check = ok`, наличие ключевых таблиц, совпадение счётчиков
с манифестом.

## 4. Восстановление

Порядок действий:

1. **Остановить сервер** (закрыть окно `ISHEIKA-NTR-AI.exe` / `Ctrl+C`).
   Восстановление перезаписывает файл БД; работающие потоки не должны его держать.
2. Проверить копию: `python3 run.py --verify-backup <ID|путь>`.
3. Выполнить восстановление с явным подтверждением:
   `python3 run.py --restore <ID|путь> --yes`.
4. Запустить программу и проверить состав данных на экране UI-31 и в журнале.

Гарантии механизма:

* без `--yes` операция отклоняется (`E_STATE`), состояние не изменяется;
* копия, не прошедшая проверку, к записи не допускается (`E_VALIDATION`);
* перед записью автоматически снимается копия текущего состояния
  (`kind = "pre-restore"`) — откат возможен всегда;
* событие `backup.restore` попадает в журнал с указанием источника и счётчиков.

Каталог данных: `%LOCALAPPDATA%\IsheikaNTR-AI` (Windows) либо `ISHEIKA_DATA`
(по умолчанию `var/`). Копии по умолчанию — `<каталог данных>/backups`.

## 5. Наблюдение

* `GET /metrics` — Prometheus: `isheika_slo_availability{window}`,
  `isheika_slo_error_budget_used{window}`, `isheika_slo_probes_total{component,ok}`,
  `isheika_slo_probe_latency_ms_avg{component}`, `isheika_alerts_open{rule,severity}`,
  `isheika_backups_total{kind}` и ранее добавленные метрики этапов и вызовов API.
* `GET /api/v1/trace/{correlation_id}` — сквозная трассировка инцидента.
* Фоновые самопроверки отключаются флагом `SETTINGS.slo_scheduler = False`
  (например, в модульных испытаниях); любой сбой наблюдения подавляется и не
  влияет на предметную работу.

## 6. Что ещё не сделано (честно)

Внешние дашборды (Grafana) и экспорт спанов OpenTelemetry, автоматическое
расписание копий и выгрузка во внешнее хранилище, периодическая проверка
восстановления «по графику», нагрузочные испытания на 100k–1M+ документов.
До их внедрения расписание копий и проверка восстановления выполняются
оператором вручную по разделам 3–4.
