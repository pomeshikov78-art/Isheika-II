## Диагностика запуска — ✅ готово (замечание пользователя: «белый экран»)

**Причина найдена и устранена.** Обработчик статики разбирал URL через
`os.path.normpath`, который на Windows превращает `/app.js` в `\app.js`;
`lstrip("/")` обратный слэш не снимает, `os.path.join` отбрасывал каталог
интерфейса — и **любой ресурс подменялся страницей `index.html`**. Браузер
получал HTML вместо CSS и сценариев: разметка есть, стили и логика не
применяются, оба контейнера остаются скрытыми → пустой белый экран.
На Linux дефект не воспроизводился, поэтому он не был виден прежним проверкам.

* разбор пути переведён на POSIX-правила независимо от ОС (`static_target`),
  с отсечением выхода за каталог и абсолютных путей Windows;
* типы содержимого задаются явно (`STATIC_TYPES`), а не берутся из реестра ОС;
* отсутствующий `.js`/`.css` — **404**, а не подмена HTML;
* `[hidden]{display:none !important}` — правила классов больше не перебивают
  скрытие контейнеров;
* при исчерпании потоков ОС — **503 с причиной** вместо обрыва соединения.

**Журнал операций при загрузке** (`isheika/boot.py`, требование пользователя):

* сервер фиксирует каждый шаг запуска (конфигурация → каталоги → БД и миграции →
  реестры → обработчики → ресурсы интерфейса → маршруты → порт → планировщик)
  и самопроверку (данные, целостность БД, реестры, ресурсы, маршруты, подсистемы);
* журнал печатается в консоль, сохраняется в `%LOCALAPPDATA%\IsheikaNTR-AI\boot-log.txt`
  и `boot-log.json`, отдаётся по `GET /api/v1/boot-log` (без аутентификации),
  `GET /api/v1/boot-log/history`, выгружается `…/boot-log/export?fmt=txt|json`;
* в браузере **экран загрузки с журналом** показывается сразу и не зависит от
  `app.js`: фиксируются загрузка каждого сценария, наличие `Charts`/`Screens`/`App`,
  ответ сервера; любая ошибка (в том числе отказ загрузки ресурса) выводится
  строкой FAIL с причиной, есть кнопки «Повторить», «Скачать журнал»,
  «Обновить журнал сервера»; сторож 12 с сообщает о неинициализированном интерфейсе;
* после входа журнал доступен кнопкой 🧾 в верхней панели (шаги сервера,
  самопроверка, ресурсы, шаги браузера, выгрузка).

Контроль: `STAT-01…07`, `BOOT-01…11`; сборка сверяет **каждый ресурс внутри
Windows-образа** с исходным файлом по размеру и типу (`--verify-wine`: 8/8);
`tools/api_check.py` проверяет типы и размеры статики и журнал; `tools/ui_check.mjs`
проверяет экран диагностики и его реакцию на отказ.

**ИД-13 (редакция 1.3.1): диагностика не должна создавать отказ сама.**
`const Charts` — лексическая привязка глобальной области, а не свойство `window`,
поэтому проверка `window.Charts` давала «FAIL Объект Charts — не определён» на
полностью рабочем интерфейсе, и экран журнала не скрывался поверх формы входа.
Модуль публикуется как `window.Charts`; диагностика видит оба способа объявления
(`B.mod`), настоящий отказ сопровождается подсказкой о невыполнившемся сценарии;
кнопка **«Продолжить работу»** скрывает журнал при готовом интерфейсе, поздние
отказы экран не перехватывают. Право на историю загрузок приведено к `logs.read`.
Подробности и прогоны — `docs/ACCEPTANCE.md`, раздел ИД-13.


## ИД-15. Исправления по журналу с машины пользователя — ✅ готово (редакция 1.4.2)

Пользователь прислал выгрузку журнала действий (`journal.json`) и лог событий
(`isheika-log.txt`) со своей машины. Журнал сработал по назначению: по подписям
дефектов и traceback найдены три настоящих ошибки, не воспроизводившиеся в тестах.

1. **`stage.source_search` → `KeyError: 'parsed_query'` (попытка 2).** Продолжение
   исследования пропускает завершённые этапы, поэтому в контексте нет живых объектов
   запроса. Добавлено восстановление из сохранённого состояния: разобранный запрос,
   расширение запроса (из сохранённой модели, а не пересборкой) и идентификатор
   запуска воспроизводимости. Испытания `RES-01`…`RES-05` воспроизводят отказ до
   исправления и подтверждают поведение после.
2. **`render.dashboard` / `render.monitor` → «Cannot set properties of null».**
   Две параллельные отрисовки одного экрана: `afterLogin` менял `location.hash`
   (отрисовка по hashchange) и сам вызывал отрисовку. Введена очередь отрисовок с
   объединением повторных запросов, безопасная запись `App.setHTML`, проверка
   устаревания после ожидания и снятие слушателей экрана при любой перерисовке.
   Испытания `RND-01`…`RND-05` и три поведенческие проверки в `tools/ui_check.mjs`.
3. **`system.error` → `FileNotFoundError … '.slo-probe'`.** Параллельные пробы
   хранилища (планировщик, загрузка, запрос API) удаляли общий файл друг у друга —
   ложный алерт `COMPONENT_DOWN`. Имя файла уникально для пробы, удаление терпимо
   к отсутствию, запись проверяется чтением. Испытание `SLO-09` (24 пробы в 4 потока).

Также устранена видимость противоречия в сводке этапа 4: добавлены `new_in_corpus`
и `known_before` — «дубль» общего корпуса не равен «дубль внутри исследования»
(`RES-06`).

**Далее:** автоматический разбор присланных выгрузок журнала (файл → находки),
подпись дефекта с привязкой к версии сборки и автоматическое сравнение с уже
закрытыми дефектами.

## ИД-14. Восстановление после недоступности сервера — ✅ готово (редакция 1.4.1)

работы» и «Журнал действий и диагностика» недоступны. Причина не в самих экранах:

отправляться навсегда (`jrnMuted`).

автопереподключение с пробой сервера и перерисовкой экрана, очередь недоставленных
событий журнала в `localStorage` с досылкой и отметкой `queued_at`, частичная
доступность экрана журнала, кнопки «Повторить» и «Переподключиться», показ очереди
в строке состояния и на вкладке «Ошибки браузера».

Испытания: `NET-01`…`NET-08`, `JRN-17` (`tests/test_offline_ui.py`) и 9 поведенческих
проверок в `tools/ui_check.mjs`, включая восстановление **по таймеру, без перезагрузки**.

**Далее:** индикатор «данные устарели» с временем последнего успешного ответа на каждом

**1. Журнал времени работы** (`isheika/journal.py`, таблица `ops_journal`, миграция
`0006_journal`). Пишутся обращения к API (метод + шаблон пути, статус, код ошибки,
длительность, актор и роль), доменные действия, события и отказы этапов, внешние вызовы
коннекторов и ИИ, необработанные исключения сервера с traceback и **ошибки браузера**
(`error`, `unhandledrejection`, отказы отрисовки, ответы `5xx`/`E_INTERNAL`/`E_SCHEMA`/
`E_PROVIDER`, сетевые отказы, FAIL-шаги загрузки). Записи связаны `request_id` /
`correlation_id` / `boot_id`; секреты маскируются до записи; повторяющиеся падения
получают подпись дефекта (`fingerprint`) и показываются одной группой; запись не может
уронить операцию (отказ БД → `var/journal-fallback.log` + счётчик сбоев); хранение
ограничено сроком и объёмом, ротация — раз в час и по требованию.

**2. Диагностика противоречий** (`isheika/diagnostics.py`, 11 правил, 21 код находок):
несогласованность состояний с конечными автоматами, «готовый» отчёт без файлов,
утверждения без доказательств и доказательства из чужого исследования, нарушение порогов
релевантности, TRL выше выполненных обязательных критериев, неизвестный фактор как число,
интерпретация при недостаточном покрытии, немонотонный прогноз и количественные оценки на
20–50 лет, платный ИИ при запрете, превышение квот, повторяющиеся дефекты и ошибки
интерфейса, похожие на секрет строки в журнале, сбои записи журнала, неизвестные версии
методик. Находка даёт число случаев, конкретные свидетельства и рекомендацию; отказ
одного правила не отменяет проверку остальными.

**3. Доступ** — 8 маршрутов API (`/api/v1/journal`, `…/stats`, `…/errors`, `…/{id}`,
`…/export?fmt=txt|json|csv`, `…/client`, `…/prune`, `/api/v1/diagnostics`,
`POST /api/v1/diagnostics/run`), экран **UI-32 «Журнал действий и диагностика»** (M33,
право `logs.read`) с четырьмя вкладками, фильтрами, карточкой записи (traceback + вся
трассировка) и выгрузкой; журнал и диагностика включены в OpenAPI 3.1 как канонические
ресурсы. Приём событий браузера публичный (без токена) с ограничением 60 событий/мин с адреса.

Испытания: `JRN-01`…`JRN-16`, `DIA-01`…`DIA-19` (`tests/test_journal.py`, 35 тестов),
проверки журнала в `tools/api_check.py` и 9 проверок экрана в `tools/ui_check.mjs`.
Правила проверяются **внесением** противоречия в данные, а не только отсутствием находок;
обратная проверка (штатное состояние не даёт находок) выявила и устранила две ложные
находки анализатора — формат версии методики «CODE version» и штатное ограничение
интерпретации при низком покрытии.

**Далее:** выгрузка журнала во внешний сборщик (syslog/OTLP) для PILOT, алерты по новым
подписям дефектов, автоматический прогон диагностики после каждого исследования,
подписывание записей журнала для юридически значимого аудита.

## Единый файл запуска — ✅ готово (задача 2)

`tools/build_exe.py` собирает `release/ISHEIKA-NTR-AI.exe`: SFX-заголовок 7zSD.sfx +
конфигурационный блок + 7z-архив со встроенным CPython 3.11 (x64) и приложением.
Установка Python на целевой машине не требуется; данные хранятся в
`%LOCALAPPDATA%\IsheikaNTR-AI`.

Запуск после распаковки — `ExecuteFile="cmd.exe"` + `ExecuteParameters="/c isheika.cmd"`
(ветка `ShellExecuteEx`). Вариант `RunProgram` непригоден: модуль выполняет его как
`CreateProcess(NULL, ".\" + RunProgram)`, из-за чего команда с аргументами даёт
ошибку «Не удается найти указанный файл» (замечание пользователя, исправлено;
регрессионные испытания `PKG-01…PKG-05`). Сценарий назван `isheika.cmd`, а не
`start.cmd`: последнее cmd разбирает как внутреннюю команду `START` и отвечает
«ShellExecuteEx failed: File not found» (обнаружено исполнением, исправлено).
Браузер открывает сама программа
(`--open-browser`), при занятом порте берётся следующий свободный (`--port-auto`).

Рядом собирается `release/ISHEIKA-NTR-AI-portable.zip` — тот же образ без SFX
(распаковать и запустить `isheika.cmd`) на случай запрета запуска SFX политикой.

Проверки сборки: структура PE/конфигурации/архива, цепочка запуска
`cmd.exe /c isheika.cmd` (`--verify-launch`), запуск образа (`--verify-wine`)
и прогон приёмочных тестов внутри образа (`--verify-tests`).

**Далее:** цифровая подпись файла (Authenticode), установщик с ярлыками и
автозапуском, вариант со встроенным PostgreSQL для PILOT.

## Приёмка промышленной версии

Численные критерии (Precision@10 ≥ 0,70; nDCG@10 ≥ 0,75; TRL MAE ≤ 1; Brier ≤ 0,20;
покрытие 90 % интервалов 85–95 %) подтверждаются **программой и методикой испытаний**
на пилотной выборке. До этого во всех экранах и отчётах выводится статус
«калибровка не завершена» — это требование ТЗ-03 §8, а не дефект.
